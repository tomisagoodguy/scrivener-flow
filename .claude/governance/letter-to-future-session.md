## 三件沒被問、但你該知道的事

### 1. 這個環境真正的敵人是「檔案只增不刪」
使用者裝了 `antigravity-reflect`、`continuous-learning`、`/reflect` 這類「自動把學到的東西寫回 CLAUDE.md」的機制。這是好習慣，但**配上「`.claude/rules/` 每 session 自動載入」，就是一台單調膨脹機**：每學一課就永久多付 token，沒有回收機制。三個月後 always-on 稅可能翻倍，弱模型開始「讀不完就跳過」，於是規則形同虛設。

**我的建議**：所有 reflect/自動學習的產出，都先過 `maintenance-protocol.md` §3–4 的閘門再落地——問「這條該 always-on 還是 on-demand？超過 §4 上限了嗎？」。把「精簡」當成和「新增」一樣正常的動作。**能刪一條過時的，比多加一條有用的更值錢。**

### 2. 設定檔在悄悄腐爛，沒人負責清
296 條 permission、大量一次性 commit-message allow 條目、只剩 1 個實際用的 MCP server 卻列舉數百個全域工具名——這些不是 bug，是**沒有維護節奏**的累積。它們現在還沒痛到讓人處理，但雜訊會拖慢每個決策。

**我的建議**：每季做一次「config hygiene」（動前問使用者，因為刪 permission 難回復）：把精確字串 allow 收斂成 pattern、停用寫程式用不到的全域連接器。這件事主對話**無法自動做**（帳號層級），只能提醒使用者——這本身就是「何時停下來問使用者」的範例。

### 3. 這套制度補得了「可靠」，補不了「品味」
拆解、多樣本、fresh-agent 驗證，能把**執行品質**做到可靠（少漏看、少手滑、有證據）。但它**補不了品味與產品判斷**：這個 UI 好不好看、這個功能值不值得做、這段文案對不對味——這些沒有測試能驗。弱模型最危險的地方，是把品味題當執行題，靜靜猜一個答案就交出去。

**我的建議**：遇到主觀/產品判斷，**別靜默猜**。要嘛升 opus 拿第二意見、要嘛把選項攤給使用者選（一次一批 ≤5 題）。明確說「這是品味題，我的預設是 X，但你可能有別的偏好」——這比假裝有標準答案誠實得多，也是 `judgment-rubrics.md` C 節的精神。

## 這套制度最可能怎麼壞掉（附預防）

### 退化模式 1（最可能）：always-on 檔膨脹到被忽略
規則太長 → 弱模型 skim → 實質不遵守 → 制度名存實亡。
**預防**：守 `maintenance-protocol.md` §4 的行數上限；每季或「覺得載入變雜」時重跑 `wc -c CLAUDE.md .claude/rules/*.md`，成長 >30% 就精簡；新內容預設放 on-demand，只有「每 3 次用到 1 次以上」才進 always-on。

### 退化模式 2：治理檔自己過時，弱模型卻照舊信
模型 ID 又改了、路徑搬了、工具改名了，但規則檔還寫舊的。弱模型不會質疑白紙黑字的規則。
**預防**：治理檔都有日期戳；沿用「推薦任何檔案/函式/旗標前，先驗證它現在還存在」的習慣（這也是 memory 系統的既有原則）。model-dispatch §0 的模型 enum 尤其要定期對照真實環境。

### 退化模式 3：驗證變成蓋橡皮章（verification theater）
「派 fresh agent 驗證」被弱模型執行成「派個 agent，它回一句 looks good，就算驗過了」。
**預防**：驗證 agent **必須回證據不回評語**——測試輸出的結尾幾行、read-back 的實際行數與關鍵段落、build 的綠燈訊息。收到「看起來沒問題」而沒有證據 → 那不是驗證，退回重驗。（見 model-dispatch §6、judgment-rubrics E。）

### 退化模式 4：分層被違反，governance/ 的東西沒人 Read
on-demand 檔的風險是「弱模型不知道自己該讀它」。
**預防**：always-on 檔（rules/ 與 CLAUDE.md）要在**觸發點**明確指路——「要派 subagent → Read delegation-templates」「要改治理檔 → Read maintenance-protocol」。指路句已埋在各 always-on 檔，維護時別把它們刪掉。
